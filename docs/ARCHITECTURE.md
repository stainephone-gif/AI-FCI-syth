# Архитектура агента синтетической редакции

Агент для Telegram-канала лаборатории ФКИ. Закрывает производство контента:
мониторинг источников, черновики постов, карточки, очередь публикаций.
Редакционные решения остаются за человеком.

## 1. Границы и инварианты

Что делает агент:

- раз в день собирает кандидатов из источников и ранжирует их по релевантности студентам ФКИ;
- пишет черновики постов в стиле канала с обязательным блоком «что это значит для медийщика» и ссылкой на источник;
- рендерит карточку к посту;
- присылает черновики в приватный редакторский чат и публикует одобренное по расписанию;
- превращает короткое сообщение редактора («в четверг семинар с ИТМО, вот ссылка») в пост;
- готовит черновики ответов на типовые вопросы в комментариях (опционально, второй этап).

Инварианты, которые не нарушаются ни при каких условиях:

1. **Ничего не уходит в канал без нажатой кнопки.** Публикатор работает только с постами в статусе `approved`, а в этот статус переводит только callback от участника редакторского чата. Пустая очередь неделю не является поводом что-либо опубликовать.
2. **Каждый факт в посте прослеживается до источника.** Модель пишет текст только по материалу, который ей передали. Названия и версии моделей, цифры, даты берутся из текста источника, иначе черновик получает пометку «требует проверки».
3. **Сгенерированный контент помечен.** Подпись в посте или отдельный тег, единый для канала.
4. **Один секрет, один владелец.** Токен бота и ключ API живут в переменных окружения на сервере, в репозитории их нет. Бот отвечает только пользователям из списка `EDITOR_IDS`.

## 2. Общая схема

```
  Источники                Ядро сервиса (Python)                     Telegram
 ┌──────────────┐       ┌─────────────────────────────┐
 │ RSS/Atom     │       │  ingest  ──►  rank  ──►  draft  ──►  card │
 │ arXiv API    │──────►│    │            │            │          │ │
 │ HSE news     │       │    ▼            ▼            ▼          ▼ │      ┌────────────────┐
 │ ACM / IEEE   │       │  ┌─────────────────────────────────────┐  │      │ Редакторский   │
 └──────────────┘       │  │        Postgres / SQLite            │  │◄────►│ чат (aiogram)  │
                        │  │ items · drafts · posts · events     │  │      │ кнопки, правки │
  Редактор в чате       │  └─────────────────────────────────────┘  │      └────────────────┘
 ┌──────────────┐       │        ▲                    │             │
 │ «в четверг   │──────►│  manual_intake         scheduler ────────►│──────► Канал (Bot API)
 │  семинар…»   │       │                        publisher          │
 └──────────────┘       └─────────────────────────────┘
                                   │
                              Claude API
                        (claude-opus-5 для текстов,
                         claude-haiku-4-5 для отсева)
```

Один процесс, один планировщик, одна база. Это сознательно: команда маленькая,
и любая распределённость станет обузой раньше, чем даст выигрыш.

## 3. Жизненный цикл поста

Каждый пост проходит конечный автомат. Переходы вправо делает код, переход в
`approved` делает только человек.

```
candidate ─► ranked ─► drafted ─► in_review ─┬─► approved ─► scheduled ─► published
                                              ├─► needs_edit ─► drafted (новая версия)
                                              └─► rejected
```

| Статус | Кто переводит | Что хранится |
|---|---|---|
| `candidate` | ingest | url, заголовок, текст, источник, хеш для дедупликации |
| `ranked` | rank | оценка 0–100, обоснование, теги |
| `drafted` | draft + card | версия текста, JSON-структура поста, путь к PNG |
| `in_review` | бот | id сообщения в редакторском чате |
| `needs_edit` | редактор | текст правки, кто и когда |
| `approved` | редактор (callback) | время публикации, кто одобрил |
| `scheduled` / `published` | publisher | id сообщения в канале |
| `rejected` | редактор | причина (опционально) |

Каждая правка создаёт новую версию черновика, старая не затирается. Так видно,
что предлагала модель и что изменил человек. Эти пары позже становятся
примерами для настройки стиля.

## 4. Компоненты

### 4.1 Ingest: сбор кандидатов

Запускается по cron раз в сутки (например, 06:00 по Москве), вручную по
команде `/collect` из чата.

| Источник | Способ | Примечание |
|---|---|---|
| Блоги OpenAI, Google, Anthropic, DeepMind | RSS/Atom (`feedparser`) | Полный текст добираем через `trafilatura` |
| arXiv | API запросы по категориям `cs.AI`, `cs.CL`, `cs.CY`, `cs.HC` | Только abstract, ссылка на PDF |
| Новости ВШЭ | RSS, где есть; иначе парсер раздела | Ломкий пункт, держать за флагом |
| ACM / IEEE по образованию и ИИ | RSS оглавлений журналов, TOC alerts | Часто paywall, берём abstract |
| Ручной ввод | сообщение боту | Обходит ranking, идёт сразу в draft |

Конфигурация источников лежит в `sources.yaml`, а не в коде, чтобы редактор
мог добавить блог без деплоя.

Дедупликация по нормализованному URL и по хешу заголовка. Один и тот же релиз,
пересказанный тремя изданиями, схлопывается в одного кандидата с несколькими
ссылками. Окно свежести: 72 часа, чтобы не пропустить пятничные новости к
понедельнику.

### 4.2 Rank: отсев и ранжирование

Кандидатов в день бывает 50–150, черновиков нужно 2–3. Ранжирование делает
`claude-haiku-4-5`: дёшево, быстро, задача простая.

Вход: заголовок, первые 1500 символов текста, источник.
Выход: structured output по схеме:

```python
class Ranking(BaseModel):
    relevance: int          # 0–100, насколько это важно студенту-медийщику
    audience_angle: str     # одна фраза: чем это касается медиа/образования
    topic: Literal["models", "tools", "media", "education", "policy", "research"]
    is_duplicate_of: str | None
    needs_fact_check: bool  # версии моделей, цифры, заявления о «лучшей модели»
```

Критерии релевантности заданы в промпте текстом и подкреплены 10–15 примерами
«взяли / не взяли» из истории канала. Порог отбора: топ-5 по `relevance`,
из них редактору уходят 2–3 после drafting. Остальные остаются в базе на
случай пустого дня.

Чтобы весь суточный батч обрабатывался одним промптом с кешем, системная
часть (критерии + примеры) фиксирована и помечена `cache_control`.

### 4.3 Draft: черновик поста

Модель: `claude-opus-5`, адаптивное мышление, `effort: "medium"`.
Один запрос на один пост. Вход собирается из трёх частей, порядок важен для
кеша:

1. **Системная часть (стабильная, кешируется).** Стайлгайд канала:
   длина 600–1200 знаков, тон, допустимые эмодзи, структура (лид, суть,
   блок «Что это значит для медийщика», ссылка), запреты (не пересказывать
   пресс-релиз, не хвалить продукт, не называть версии моделей без источника).
   Три эталонных поста целиком: про пять моделей, про ELIZA, про стартерпак.
2. **Материал.** Полный текст источника, дата, ссылка, `audience_angle` из
   ранжирования.
3. **Задание.** Написать пост по схеме ниже.

Выход через `client.messages.parse` по схеме:

```python
class Post(BaseModel):
    headline: str                    # первая строка, до 80 знаков
    body: str                        # текст поста с разметкой Telegram HTML
    media_takeaway: str              # блок «Что это значит для медийщика»
    source_url: str
    claims: list[Claim]              # факты, на которых стоит пост
    card: CardSpec                   # заголовок и подзаголовок для карточки
    confidence_notes: list[str]      # что модель не смогла подтвердить
```

```python
class Claim(BaseModel):
    text: str        # утверждение из поста
    quote: str       # дословная цитата из источника, на которую оно опирается
```

Поле `claims` — основа защиты от выдуманных фактов. Код проверяет, что каждая
`quote` действительно встречается в тексте источника (нечёткое совпадение,
порог 0.85). Утверждение без подтверждения не удаляется, а подсвечивается в
редакторском чате: «⚠️ не нашёл в источнике: …». Решение остаётся за человеком.

Правка: редактор отвечает на сообщение с черновиком текстом. Бот отправляет
в модель предыдущую версию, правку и стайлгайд, получает новую версию,
присылает её с теми же кнопками. Мелкие правки (заменить слово, убрать
абзац) редактор может делать и без модели, отправив полный текст с командой
`/replace`.

### 4.4 Card: карточка

HTML-шаблон в фирменном стиле (Jinja2) → Playwright/Chromium → PNG 1080×1350.
Шаблонов несколько: «новость», «исследование», «анонс лаборатории», «пять
моделей». Шаблон выбирается по `topic`. Шрифты и логотип лежат в репозитории,
внешних запросов при рендере нет, поэтому карточка рендерится и без сети.

Альтернатива для более сложной графики: Gamma через коннектор. Для ежедневных
постов избыточно, но подходит для лонгридов и рубрики «пять моделей».

### 4.5 Редакторский чат (aiogram)

Приватная группа или личный чат с ботом. Доступ по allowlist `EDITOR_IDS`.
Сообщение от чужого пользователя игнорируется без ответа.

Утренний дайджест (например, 09:00): 2–3 сообщения, каждое = карточка +
текст + inline-кнопки:

```
[ Опубликовать 12:00 ]  [ Опубликовать 18:00 ]
[ Другое время ]        [ Отредактировать ]     [ Отклонить ]
```

Команды:

- `/collect` — внеплановый сбор;
- `/queue` — что стоит в очереди и на когда;
- `/cancel <id>` — снять из очереди до публикации;
- `/post <текст>` или просто сообщение со ссылкой — ручной ввод, из которого
  агент делает пост (новости лаборатории, наборы, студенческие работы);
- `/five <вопрос>` — рубрика «Объективности не существует»: вопрос прогоняется
  через пять моделей, результат оформляется в пост и карточку.

Состояние диалога (ждём правку, ждём время) хранится в FSM aiogram,
привязано к id черновика.

### 4.6 Scheduler и Publisher

APScheduler с хранилищем задач в той же базе. Планировщик держит два вида
задач: cron (сбор, дайджест) и одноразовые (публикация в назначенное время).

Publisher перед отправкой перечитывает пост из базы и проверяет статус
`approved`. Если статус изменился (редактор снял), задача завершается без
публикации. Отправка через Bot API: `sendPhoto` с caption, если текст помещается
в 1024 знака, иначе `sendPhoto` + `sendMessage`. После успеха сохраняется
`message_id` канала, чтобы потом можно было отредактировать или удалить пост
командой из чата.

Идемпотентность: у каждой публикации есть `publish_key`, повторный запуск задачи
с тем же ключом ничего не отправляет.

### 4.7 Ручной ввод от редактора

Сообщение вида «в четверг семинар с ИТМО, вот ссылка» проходит тот же
draft-шаг, но с другим шаблоном задания: событие, дата, участники, что делать
читателю. Даты нормализуются относительно текущей («в четверг» → конкретное
число), и результат показывается редактору для подтверждения, потому что
здесь ошибка в дате дороже всего.

### 4.8 Ответы в комментариях (второй этап)

Бот получает комментарии из группы обсуждений канала, классифицирует
(вопрос / реплика / спам), для вопросов из FAQ (`faq.md` в репозитории)
готовит черновик и присылает его в редакторский чат с кнопкой «Ответить».
Самостоятельно бот в комментарии не пишет.

### 4.9 Рубрика «пять моделей»

Отдельный пайплайн: один вопрос → параллельные запросы к пяти моделям через их
API (Claude, OpenAI, Gemini, и два по выбору) → таблица ответов → пост с
сопоставлением и карточка-сетка. Точные названия моделей берутся из ответа
API (`model` в ответе), а не из промпта, чтобы в посте была та версия, что
реально отвечала.

## 5. Данные

Postgres в проде, SQLite в разработке (через SQLAlchemy разница только в URL).

```
sources   id, name, kind(rss|arxiv|html|manual), url, enabled, last_polled_at
items     id, source_id, url, url_hash, title, text, published_at, fetched_at
rankings  item_id, relevance, audience_angle, topic, needs_fact_check, model, created_at
drafts    id, item_id, version, post_json, card_path, model, prompt_version, created_at
posts     id, draft_id, status, scheduled_at, published_at, channel_message_id,
          approved_by, publish_key
events    id, post_id, actor(user_id|system), action, payload, created_at
```

`events` — журнал всего, что происходило с постом: кто одобрил, что правил,
когда опубликовали. Это и аудит, и материал для улучшения промптов.

`prompt_version` в `drafts` нужен, чтобы при изменении стайлгайда было понятно,
какие черновики написаны по какой версии.

## 6. Промпты и качество

Все промпты лежат в `prompts/` как файлы, а не строки в коде. Стайлгайд и
эталонные посты — в `prompts/style/`. Редактор может править их через PR.

Порядок сборки запроса фиксирован (стабильное → изменчивое), чтобы кеш
промпта отрабатывал: стайлгайд + примеры кешируются, материал и задание идут
после точки кеша.

Оценка качества: раз в месяц прогоняем 20 случайных источников из базы через
текущие промпты и сравниваем с тем, что в итоге опубликовали (после правок
редактора). Метрики простые: доля черновиков, принятых без правок; средний
объём правки; число фактов, помеченных как неподтверждённые.

## 7. Расписание типичного дня

| Время (МСК) | Что происходит |
|---|---|
| 06:00 | ingest: сбор, дедупликация |
| 06:15 | rank: оценка кандидатов |
| 06:30 | draft + card для топ-3 |
| 09:00 | дайджест в редакторский чат |
| 09:00–09:15 | редактор нажимает кнопки, правит |
| 12:00 / 18:00 | publisher отправляет одобренное |
| по событию | ручной ввод, правки, отмены |

Если к 09:00 нет ни одного кандидата выше порога, бот пишет об этом одной
строкой и ничего не предлагает.

## 8. Безопасность и доступ

- Токен бота, ключи API в `.env` на сервере, в репозитории `.env.example`.
- Права бота в канале: только публикация и редактирование своих сообщений.
- Allowlist редакторов по Telegram user id; список в конфиге, не в коде.
- Callback-данные кнопок подписаны (HMAC от `post_id` + действие), чтобы нельзя
  было одобрить пост, подделав callback.
- Логи без текстов источников целиком, только id и статусы.
- Кнопка «Опубликовать» на посте с неподтверждёнными фактами требует второго
  нажатия («Опубликовать, несмотря на ⚠️»).

## 10. Оценка стоимости

При 100 кандидатах и 3 черновиках в день:

| Шаг | Модель | Токенов в день (приблизительно) | Стоимость в месяц |
|---|---|---|---|
| rank | claude-haiku-4-5 | 100 × ~1.5k вход, ~0.1k выход | ~$5 |
| draft | claude-opus-5 | 3 × ~8k вход (большая часть из кеша), ~1.5k выход | ~$5 |
| правки | claude-opus-5 | 3 × ~6k вход, ~1k выход | ~$3 |

Итого порядка $10–20 в месяц на API. Сервер — VPS за $5–10. Основная
стоимость проекта — время разработчика на первую неделю.

## 11. Этапы

**MVP (1 неделя).** RSS-источники, ранжирование, черновик, карточка по одному
шаблону, редакторский чат с тремя кнопками, публикация по расписанию, ручной
ввод. Достаточно, чтобы вести канал.

**v1 (ещё 1–2 недели, по мере надобности).** arXiv и ВШЭ, проверка цитат по
источнику, версии черновиков, команда `/five`, метрики качества.

**v2.** Черновики ответов в комментариях, несколько шаблонов карточек, Gamma
для лонгридов, интеграция с расписанием лаборатории (календарь → анонсы).

## 12. Принятые решения и открытые вопросы

Принято:

1. **Хостинг.** Начинаем с VPS (арендованный виртуальный сервер). Переезд в
   инфраструктуру университета рассматриваем после того, как агент отработает
   первый месяц. Требование к серверу: доступность API моделей из его сети.
2. **Пометка сгенерированного контента.** Сочетание: короткая строка или тег
   в конце каждого поста плюс закреплённое сообщение с описанием процесса.
   Строка едет с постом при пересылке, закреп объясняет подробности.
3. **Одобрение.** Два редактора с правом одобрения. Обычный пост публикуется
   по одному нажатию. Пост с пометкой ⚠️ требует нажатия от второго редактора:
   первый нажимает «Опубликовать», бот просит подтверждение у другого.

Открыто:

1. Нужен ли отдельный порог релевантности для источников об образовании
   (ВШЭ, ACM SIGCSE), чтобы они не проигрывали громким релизам моделей.
   Решим после первых двух недель работы, когда будет видно, что отсеивается.

## 13. Пошаговый план запуска

Шаги делятся на те, что может сделать только редакция, и те, что делает
разработчик. Первые не требуют программирования.

### Редакция, до начала разработки

1. **Создать бота.** В Telegram написать @BotFather, команда `/newbot`,
   сохранить токен. Токен никому не пересылать в открытом виде.
2. **Дать боту права.** Добавить бота администратором в канал с правом
   публиковать сообщения. Создать приватную группу «Редакция», добавить туда
   бота и обоих редакторов.
3. **Узнать user id редакторов.** Написать боту @userinfobot, он ответит
   числом. Эти два числа попадут в allowlist.
4. **Завести ключ API моделей** и передать разработчику тем же защищённым
   способом, что и токен бота.
5. **Арендовать VPS.** Минимальный тариф: 2 ядра, 2 ГБ памяти, Ubuntu.
   Разработчику нужен доступ по SSH.
6. **Собрать стайлгайд.** Один документ с ответами: длина поста, тон,
   какие эмодзи допустимы, что запрещено, как оформляется ссылка на источник,
   как выглядит блок «Что это значит для медийщика». Три эталонных поста
   целиком: про пять моделей, про ELIZA, про стартерпак.
7. **Составить список источников.** Ссылки на блоги и RSS, категории arXiv,
   разделы новостей ВШЭ. Для каждого одна строка: почему он нужен каналу.
8. **Подобрать 10–15 примеров «взяли / не взяли».** Заголовки новостей за
   последние месяцы с пометкой, подошли бы они каналу или нет, и одной фразой
   почему. Это учебный материал для ранжирования.
9. **Написать текст пометки и закрепа.** Строка для конца поста и абзац для
   закреплённого сообщения.

### Разработка

10. **Скелет сервиса.** Структура репозитория, конфиг, база, бот, который
    отвечает только редакторам из allowlist. Деплой на VPS одной командой.
11. **Сбор и ранжирование.** Источники из `sources.yaml`, дедупликация,
    оценка кандидатов. Проверка: бот по команде `/collect` присылает список
    из десяти лучших заголовков с оценками.
12. **Черновики и редакторский чат.** Генерация поста по стайлгайду, кнопки
    «опубликовать / отредактировать / отклонить», правка ответом на сообщение,
    подсветка неподтверждённых фактов.
13. **Публикация по расписанию.** Очередь, отмена, идемпотентность,
    второе одобрение для постов с ⚠️.
14. **Карточки.** Один шаблон в фирменном стиле, рендер в PNG.
15. **Ручной ввод.** Сообщение о событии превращается в пост, даты
    подтверждаются редактором.

### Запуск

16. **Тестовая неделя** на закрытом канале-дублёре. Редакция работает как в
    бою, разработчик правит промпты и шаблон по замечаниям.
17. **Переключение на боевой канал.** Закреп с описанием процесса, первый
    пост с пометкой.
18. **Через две недели.** Разбор: сколько черновиков принято без правок, что
    отсеялось зря, нужен ли отдельный порог для образовательных источников.
